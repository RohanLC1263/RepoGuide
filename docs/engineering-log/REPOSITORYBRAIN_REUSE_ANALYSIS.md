## Part A — RepositoryBrain: does it need to be built from scratch?

### Target contract

`ARCHITECTURE_FREEZE.md` Part 3 requires: a `RepositoryKnowledge` schema (confidence with numeric score + source breakdown, provenance, recomputable freshness, an 8-state lifecycle `candidate→validated→promoted→active→stale|contradicted→retired→archived`, `validationState`, non-empty `supportingEvidence` once promoted/active, preserved `contradictions`), a 10-method API (`observe/validate/promote/retrieve/query/explain/invalidate/refresh/retire/forget`), and local-first, schema-versioned, crash-recoverable storage where "active knowledge may become stale or contradicted, never silently overwritten."

### The storage picture that changes the verdict

- **The actual production database**, `.repoguide/repository_brain.sqlite` (path from `src/preparation/repositoryPaths.ts:35`, opened by `src/mcp/mcpServer.ts:197`), contains **only 3 tables — `prediction_metrics`, `prediction_outcomes`, `prediction_snapshots` — all with 0 rows.** These are exactly and only the schema created by `PredictionAccountabilityStore.initializeSchema()`, which `RepositoryBrainEvidenceStore`'s constructor instantiates unconditionally. None of `decision_outcomes`, `causal_explanations`, `incident_events`, `knowledge_hotspots`, or any runtime-intelligence table exist in the live database at all.
- **Why:** the only code path that ever creates those tables is `RepositoryBrainOrchestrator.runFullRebuild()` → the individual builders' store constructors — and that orchestrator is never invoked in production (test-only, confirmed above). `CausalReasoningStore` specifically is permanently mocked inside `RepositoryBrainEvidenceStore`, so its tables are never created under any circumstances, test or production.
- **Practical consequence:** every query `RepositoryBrainEvidenceStore.execute()` runs against `decision_outcomes`/`causal_explanations`/`incident_events`/etc. throws `no such table` in the live database, silently caught and logged via `console.error`. `RepositoryBrainProvider.retrieve()` almost always returns `status: 'empty'` in real usage today. The sophisticated builder logic documented above is real and non-trivial, but **it is not currently reaching users** — the orchestrator that would populate it is disconnected from the runtime it's supposed to serve.
- No other RepositoryBrain-related persistent store exists anywhere in the repo (exhaustive search found exactly these two `.sqlite` files). `.repoguide/` holds other, unrelated stores (`logical_units.db`, `facts.db`, `bm25_index.json`, LanceDB) that are not RepositoryBrain-owned.

### Revised conclusion

**The prior "Not Yet Implemented" verdict on API/schema/lifecycle conformance stands exactly as stated** — nothing here contradicts it. The 10-method API, 8-state lifecycle, and `RepositoryKnowledge` schema genuinely do not exist in any form and must be designed and built new.

But **"build RepositoryBrain from scratch" overstates what needs to be thrown away**, and risks discarding real, working analytical logic that would be expensive to re-derive:

1. **The domain/scoring logic is real, not stub code.** `causalReasoningBuilder.ts`, `decisionOutcomeBuilder.ts`, and especially `incidentIntelligenceBuilder.ts` contain carefully constructed, evidence-weighted confidence and risk calculations (log-scaled evidence confidence, noisy-OR multi-signal risk fusion, window-function trend detection, chain-relationship inference) that already do informally much of what the frozen contract's confidence-update rules ask for.
2. **The bigger problem this inspection surfaced is disconnection from production, not absence of logic.** The live database is nearly empty because the one thing that would populate it is wired into tests only. This means today's "Not Yet Implemented" framing actually *undersells* severity in one respect (real users get silent empty results from a subsystem the frozen doc's query-category mapping rules assume is contributing) while *overselling* it in another (the code that would produce real value, if wired up, already exists).
3. **The archived SQLite file confirms it holds nothing worth migrating** — delete it; it costs nothing.

**Recommendation carried into Part C:** don't build RepositoryBrain from scratch. Build the `RepositoryKnowledge` schema, 8-state lifecycle, and 10-method API as a new wrapper/orchestration layer; rewire the existing `RepositoryBrainOrchestrator` into a real production trigger so it actually populates the store; adapt (not rewrite) the confidence/risk logic in the three builder files to write into lifecycle-aware records instead of destructively overwriting flat tables on every rebuild. `RepositoryBrainEvidenceStore`'s fan-out pattern and `RepositoryBrainProvider`'s `evidenceTypes` taxonomy are reusable as internal implementation details behind the new public API.

## Part B — HybridRetrievalFusion vs. the legacy pipeline: what's actually entangled

### 1. Does `HybridQueryPipeline` share retrieval code with the evidence path, or duplicate it?

**Neither exactly — it shares the *class*, not the *instance*.** `HybridQueryPipeline`'s constructor instantiates its own `HybridRetrievalFusion` (`hybridQueryPipeline.ts:61-73`) and calls only its high-level orchestration methods — `this.fusion.query(...)` (`:104`) and `this.fusion.explainSelection(...)` (`:147-154`) — never the low-level ad hoc API (`retrieveContext`, `searchBm25Evidence`, etc.) directly.

In `src/extension.ts`, **two separate `HybridRetrievalFusion` instances** are constructed — `phase10Fusion` for the evidence path (`:432-444`, wrapped by `HybridRetrievalProvider` at `:449`) and one built inside `HybridQueryPipeline`'s own constructor for the legacy path (`:473-486`) — but both are constructed with the *identical variable references* for `store`, `bm25Store`, `symbolIndex`, `importGraphSearcher`, `comprehensionEngine`, `history`, and `notesManager`. So both instances wrap the same underlying data stores; there are just two live objects running the same retrieval code independently, not one shared object and not two different retrieval algorithms.

**Additional finding:** `HybridRetrievalFusion`'s low-level API has two more direct callers beyond the audited two — `InvestigationEngine` (`extension.ts:464`) and `PlanAnalyzer` (`extension.ts:471`), both constructed against the evidence-path's `phase10Fusion` instance, powering `/investigate` and plan-analysis. Neither calls `AnswerGate` either. These are a separate concern from the legacy/evidence split but confirm the ad hoc retrieval API has a wider blast radius than the two pipelines alone.

### 2. Is retrieval physically separable from answer-generation?

**At the `HybridQueryPipeline` ↔ `HybridRetrievalFusion` boundary: yes, cleanly.** `hybridQueryPipeline.ts` contains zero retrieval logic of its own — no direct BM25/vector calls anywhere in the file; 100% of retrieval is delegated.

**But inside `HybridRetrievalFusion` itself, retrieval and answer-synthesis are interleaved in the same methods — this is the real seam, one level deeper than the earlier conformance audit looked.** `HybridRetrievalFusion.query()` (`:786-919`) in one method: calls `retrieveContext()` (`:787`) for retrieval, builds an LLM prompt via `buildChatMessages()` (`:863-875`), **directly invokes the LLM** via `streamChat()` inline (`:892-895`), and builds provenance/metadata inline (`:853-861, 897-909`). `explainSelection()` (`:921-1066`) follows the identical pattern. Neither method, nor `hybridQueryPipeline.ts`, ever imports `AnswerGate`.

The true architectural boundary is therefore not "HybridQueryPipeline vs. HybridRetrievalFusion" but **"HybridRetrievalFusion's pure-retrieval method (`retrieveContext` + private search helpers, lines 100-784) vs. HybridRetrievalFusion's own `query()`/`explainSelection()` orchestration methods (lines 786-1066)"** — the latter fuse retrieval + prompting + LLM invocation + provenance into one monolithic flow with no validation step. By contrast, the evidence path keeps retrieval, synthesis, and validation in three separate classes connected only through the typed `EvidencePacket` boundary — a materially cleaner separation than what exists inside `HybridRetrievalFusion` today.

### 3. What does "legacy" actually mean at the retrieval layer?

**Confirmed: case (a) from the original question — same retrieval code, different post-processing, not duplicate retrieval.**

- **Evidence path:** `RetrievalOrchestrator.execute()` → `HybridRetrievalProvider.retrieve()` calls **only** `fusion.retrieveContext()` (`hybridRetrievalProvider.ts:83-86`) → `EvidencePacketBuilder.buildPacket()` → `EvidenceAnswerSynthesizer.synthesize()` (separate prompt builder, `evidencePrompt.ts`) → `AnswerGate.verify()` (can block the answer).
- **Legacy path:** `HybridQueryPipeline.query()` → `HybridRetrievalFusion.query()` calls `this.retrieveContext()` (`hybridRetrievalFusion.ts:787`) — **the same method**, same code, on a different instance of the same class, against the same underlying stores — then builds messages via a different prompt builder (`chatPrompt.ts`), calls `streamChat()` inline, and never calls `AnswerGate`.

Both paths call the identical `retrieveContext()` method. They diverge immediately *after* retrieval. There is no separate/duplicate retrieval implementation in the legacy path — the "duplication" is two live instances of the same retrieval class, not two different retrieval algorithms.

### 4. Does `EvidencePacketBuilder` call `HybridRetrievalFusion` directly too?

**No — confirmed by a full read of the 600-line file.** No import of `HybridRetrievalFusion`, no reference to any of its methods. `buildPacket()` only *consumes* an already-computed `RetrievalOrchestrationResult` passed in as a parameter (produced upstream by `RetrievalOrchestrator.execute()`, which is what actually calls `HybridRetrievalProvider`). `EvidencePacketBuilder`'s own retrieval steps hit a fully separate stack — `LogicalUnitStore`, `FactStore`, `LogicalUnitBm25Store` (a *different* BM25 store from the chunk-level one `HybridRetrievalFusion` uses), `ProgramGraphStore`, `FileAnnotationEngine`, and direct filesystem reads — none of which touch `LanceStore`, the chunk-level `Bm25Store`, or `HybridRetrievalFusion`.

**Notable dead wiring found in passing:** `EvidencePacketBuilderStores` declares a `lanceStore: LanceStore` field (`:46`), wired at `extension.ts:607` to the same store instance `HybridRetrievalFusion` uses, but `this.stores.lanceStore` is never referenced anywhere in `evidencePacketBuilder.ts`. It's unused wiring, not an active path — cheap to remove, currently harmless.

**Answer:** only two callers of `HybridRetrievalFusion`'s retrieval methods within the core chat-answer flow (legacy pipeline's own instance; `HybridRetrievalProvider`'s evidence-path instance). `EvidencePacketBuilder` is not a third — it consumes `HybridRetrievalProvider`'s already-produced output, mixed with independent LogicalUnit/Fact/ProgramGraph retrieval.

### 5. What would it take to delete `HybridQueryPipeline` entirely?

Two legacy-only capabilities need new homes in the evidence path:

**(A) `explainSelection` / `explainSelectionResult`.** Currently `QueryDispatcher.explainSelection()` unconditionally delegates to legacy (`queryDispatcher.ts:310-321`), even though `HybridRetrievalProvider.capabilities.queryCategories` already *advertises* `'explain_selection'` (`hybridRetrievalProvider.ts:33`) — nothing currently routes to exercise that advertised capability. Needed: (i) a selection-seeded planning entry point (`ExecutionPlanner.plan()` currently only accepts a free-text `query: string`; the selection-to-query-terms logic that exists today in `HybridRetrievalFusion.explainSelection()`, lines 945-970, would need to move into a pre-processing step or a new planning mode), (ii) a selection-specific prompt builder consuming an `EvidencePacket` (mirroring `buildEvidenceMessages` but for explain-selection framing), (iii) anchor-vs-related-chunk mapping logic reconstructed from `EvidenceItem`s (no such distinction exists in `EvidencePacket` today). Reused unchanged: `RetrievalOrchestrator`, `EvidencePacketBuilder`, `AnswerGate`, and `HybridRetrievalProvider` itself.

**(B) Conversation-history handling.** This is a genuine capability gap, not just a wiring difference — `QueryDispatcher` has no `ConversationHistory` dependency at all today (confirmed by grep: no `history`/`History` token anywhere in the file), while `HybridQueryPipeline`/`HybridRetrievalFusion` thread it through the whole flow and write back after each turn. Needed: (i) thread a `ConversationHistory` instance into `QueryDispatcher`'s constructor (straightforward — `extension.ts` already builds one shared instance passed to both pipelines today), (ii) call `history.add(...)` after synthesis in `runEvidenceQuery()`, (iii) extend `buildEvidenceMessages()` to render prior turns into the prompt, (iv) **a real design decision, not just code**: decide whether follow-up questions get history-aware query rewriting before planning, or whether `ExecutionPlanner` itself becomes history-aware — neither exists today and the codebase doesn't determine which is preferable.

**Net effect once (A) and (B) are done:** `HybridQueryPipeline` and `HybridRetrievalFusion`'s `query()`/`explainSelection()` orchestration methods (everything except `retrieveContext()` and its private helpers) become deletable dead code, along with the `legacyPipeline` branch in `QueryDispatcher.query()` and the `repoguide.queryArchitecture` setting. `hybridRetrievalFusion.ts` itself is **not** fully deletable — its pure-retrieval surface remains load-bearing for `HybridRetrievalProvider`, `InvestigationEngine`, and `PlanAnalyzer`.

This is a materially smaller job than "merge two retrieval systems" — the retrieval systems are already one system. The work is porting two capabilities and deleting an orchestration wrapper, not reconciling divergent retrieval implementations.
