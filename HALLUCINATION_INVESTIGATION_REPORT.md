# Hallucination Investigation Report — CraftConnect Manual Test

Investigation only — no fixes applied. Follows up on two confirmed fabrications found during manual UI testing against CraftConnect:

1. Claimed `story_generation_agent.py`/`story_gen_agent.py` are "identical, no functional difference" — false; `story_gen_agent.py`'s own docstring says it's a deprecated compatibility shim.
2. Printed a fabricated ~20-line `__init__` as quoted code from `orchestrator_agent.py` — the real file is a 24-line stub that raises `RuntimeError`. The fabricated code was verbatim-identical to `MissionOrchestratorAgent`'s real constructor. A later question in the same session correctly described the real `orchestrator_agent.py`.

Tool used: `src/evaluation/hallucinationInvestigation.ts`, which reruns both questions through the real `QueryPipelineHarness`/`QueryDispatcher`/`AnswerGate`/`EvidencePacketBuilder` production path, and monkey-patches `EvidencePacketBuilder.prototype.buildPacket` **from within the script itself** (no production file edited) to capture the exact `{file, content}` pair for every evidence item passed to the model.

## 1. Reproduction — did not reproduce

Both questions were run **3 times each** (6 total) against the current index, at the production-configured `temperature: 0` (confirmed in `src/ollama/inferencer.ts:8,14`). **All 6 runs produced correct, honest answers** — no fabrication recurred:

- Both `dup-story-agent` runs: "the evidence does not determine... which one is used in the mission pipeline" — correctly described both classes, did not claim they're identical.
- All 3 `dup-orchestrator` runs: correctly identified `orchestrator_agent.py` as "prevents accidental imports of legacy OrchestratorAgent" / "legacy or older version."

**This is itself an important, honest finding: the fabrication is not a stable, deterministically-reproducible defect.** It happened once, in the manual UI session, and did not recur across 6 attempts via the identical production code path. That constrains which of the two original hypotheses is plausible — see below.

## 2. Evidence trace for the orchestrator fabrication

Inspected every captured evidence item for `orchestrator_agent.py`, `mission_orchestrator.py`, and `mission_coordinator.py` across all 3 reproduction runs. Result: **retrieval and storage cleanly and correctly separate content per file, every time.**

- Every `orchestrator_agent.py` item correctly contains its real stub content: `raise RuntimeError("Legacy OrchestratorAgent has been removed...")`.
- Every `mission_orchestrator.py` item correctly contains its real constructor (`classifier_agent, rag_agent, story_agent, packager_agent...`).
- Same clean separation confirmed for `story_generation_agent.py` vs `story_gen_agent.py` — the deprecation annotation ("Provides a compatibility shim for deprecated StoryGenAgent") was present and correctly attributed in every run.

**This rules out hypothesis (a), the data-integrity/mislabeling bug.** Nothing in storage or retrieval attaches one file's content to another file's identity. The fabrication, wherever it came from, was not caused by corrupted or cross-wired chunk metadata.

This leaves hypothesis (b), a faithfulness failure, as the better-supported explanation — with one important nuance surfaced along the way (item 5 below): with 149–174 files cited per query for these multi-file comparison questions, only a small subset (`profile.maxChunks`, a low single-to-double-digit number) actually survives `trimToTokenBudget()` into the final prompt (`src/query/tokenBudget.ts`). The dedup/scoring step upstream of that trim (`[Deduplication Trace] Existing score: 1, New score: 0.9`-style comparisons, visible in the logs) resolves near-ties based on the order concurrent retrieval providers complete — which is not guaranteed identical run-to-run. So while I can't recover the exact historical prompt that produced the fabrication, there is a concrete, code-confirmed mechanism by which the *same* question could receive a *different* trimmed evidence subset across sessions, independent of temperature. That's consistent with a rare, state-dependent faithfulness slip rather than either "always broken" or "purely random model noise."

## 3. hallucinationGuard.ts — confirmed unwired, not just weak

Previously characterized as "existence-only" verification. Full picture, confirmed by exhaustive grep: **`src/ui/hallucinationGuard.ts` is imported nowhere in `src/`, and its two exported functions (`verifyLocations`, `verifyNavigationTargets`) are called nowhere** — not in the real chat path, not in the eval harness, not anywhere. The only reference to the file anywhere in the codebase is a comment in `src/evaluation/scorers.ts:220` explicitly noting that a different heuristic "deliberately does NOT reuse hallucinationGuard.ts's citation-existence check."

This is a stronger finding than the working hypothesis: it's not that a weak (existence-only) guard lets fabrications through — **no guard from this file runs at all, in any path.** This matches the pattern CLAUDE.md already documents for this repo (`src/intent/`, `src/evolution/`, `src/drift/`, `src/causal/` — fully built, fully tested, never wired to anything that runs).

## 4. The real gate — `AnswerGate`, confirmed with a genuine structural blind spot

Traced from `queryDispatcher.ts:130` (`this.answerGate = new AnswerGate()`) — this is the actual, wired, production verification step, invoked in the real chat path. Read `src/query/answerGate.ts` in full. It checks numeric claims, quoted strings, file paths, and fallback-chain ordering — this is what produced every "Gap: Unsupported numeric claim" / "Symbol appeared out of order" message seen in both dogfood passes.

**Confirmed structural gap, directly relevant to both fabrications**: the quoted-string check (line 122-141) and file-path check (line 143-159) both validate against a **global pool** — `allContent` (every evidence item's content, from every cited file, concatenated) and `allFiles` (every cited file path, as a flat set). Neither check ties a specific quoted string to the specific file the surrounding prose claims it came from. Concretely: if `mission_orchestrator.py`'s real `__init__` code is *anywhere* in the evidence pool (which it legitimately was, since the question asked about it too) and `orchestrator_agent.py` is *anywhere* in the cited-files set (which it also legitimately was), then an answer falsely attributing the former's code to the latter's file passes both checks — the quote is "supported" (it appears somewhere) and the path is "supported" (it was cited somewhere). This is a real, confirmed, exploitable blind spot independent of whether it's what caused this specific historical instance.

## 5. Confidence scoring — corrected finding, and the avgScore thread closed

**Correction to the prior investigation pass**: `src/query/confidenceScorer.ts`'s `score()` function is not what's live in the real chat path — confirmed by grep, it is never called anywhere in `src/`; only its `ConfidenceResult` *type* is imported (by `queryDispatcher.ts` and `evaluation/types.ts`). The actual, wired confidence computation is `computeEvidenceConfidence()`, defined locally in `queryDispatcher.ts:66-87`.

Its formula: `avgScore` = mean of every evidence item's/fact's `.score` field; `level` is `'high'` only if `packet.coverageScore >= 0.75 AND avgScore > 0.75 AND itemCount >= 3`, `'medium'` if `coverageScore >= 0.4 AND avgScore > 0.5`, else `'low'`. **Same structural finding as before holds**: this formula has no input at all from the generated answer text — it cannot reflect whether the answer's claims match the evidence, only whether the evidence itself looked strong by retrieval-relevance and coverage metrics.

Closing the specific thread — why "Low" fired here despite seemingly on-topic retrieval: my own harness-based reproduction could not directly recompute this value, because `QueryPipelineHarness` never wires the `onConfidence` callback that `QueryDispatcher.query()` accepts (confirmed: `queryPipelineHarness.ts:303` hardcodes `confidence: null` — the harness simply doesn't capture it, a gap in this diagnostic tooling, not in RepoGuide). But the formula itself explains the pattern without needing the exact number: `itemCount` was never the limiting factor (149+ items every time) — `'low'` requires either `coverageScore < 0.4` or `avgScore <= 0.5`. A three-way disambiguation question spanning three similarly-named files is exactly the shape of query where a coverage heuristic tuned for single-topic evidence would plausibly score low, **regardless of whether the eventual answer is faithful or fabricated** — both the fabricated run and all 6 honest reproductions are the same query shape and would be expected to hit the same low-coverage path. **The practical conclusion**: "Low" confidence in this UI does not carry a specific hallucination-risk signal — it's an artifact of query breadth/coverage, not answer trustworthiness, and a user has no way today to distinguish "Low because this is a hard multi-file question, honestly answered" from "Low because the model may have guessed."

## 6. call_graph_v2 86% unresolved / 28% partial-parse

Read `src/comprehension/callGraph/edgeResolver.ts` in full. Resolution proceeds through four strategies in order: `resolveContainerPattern` (a single regex, `/self\.(?:container\.)?(\w+)\.(\w+)/`, matching dependency-injection-style calls, with the target file located only via crude string-inclusion matching between the DI attribute name and candidate file/class names), `resolveSameFile`, `resolveViaImports`, `resolveGlobal` — the latter three all require an exact, unambiguous (single-candidate) name match, and immediately give up (mark unresolved) on any ambiguity (more than one candidate) or any unmatched import path.

No baseline figure for this metric exists anywhere in this repo's prior reports (confirmed — grepped every `.md` file for "resolved edges"/"unresolved edges"/percentage phrasing; zero matches), so I cannot say authoritatively whether 86% unresolved is unusual in absolute terms. What I can say from reading the resolver: CraftConnect's actual architecture — heavy constructor-injected multi-agent dispatch (`self.container.listing_assistant.generate_draft()`, `self.coordinator.run_mission()`, seen directly in the evidence traces above) — is precisely the shape of code this resolver handles most narrowly. The container-pattern regex only recognizes one exact call shape and depends on a fragile name-similarity heuristic; everything else requires zero ambiguity. A codebase built around passing collaborator objects through constructors (rather than static imports or same-file calls) will systematically miss the other three resolution strategies at the call sites that matter most for tracing a mission's actual flow — which plausibly explains why flow-tracing and decision-outcome questions were the ones that kept surfacing "Gap" failures in both dogfood passes. This is a reasoned, code-grounded explanation, not a measured comparison — a genuine before/after or cross-repo number would require running the same builder against a codebase with a different call style, which is out of scope here.

## 7. Retrieval-precision issues — unchanged, lower priority

As previously noted: the LLM fallback-order question missed evidence that existed verbatim in the index (`"Fallback chain: Gemini → Groq → Ollama → Mock"` inside `story_generation_agent.py`), and several answers cited plainly irrelevant "top sources" for the question asked. Not investigated further this pass — distinct problem from the fabrication, lower severity.

## Recommendation

**Yes, a live content-verification step is sufficient to close both confirmed fabrications — with one scope caveat.**

For the **orchestrator `__init__` fabrication**: a verification step that re-reads the actual cited file fresh from disk and confirms any quoted/paraphrased code genuinely appears at (or near) the cited location, before the answer is shown, closes this regardless of which root cause applies. If the cause was truncation-driven evidence-selection variance, the fix still works because it operates downstream, on the final claim against the real file — not on whatever subset of evidence the model happened to see. If the cause was a rarer generation-level slip despite correct evidence, the fix still works for the same reason: it doesn't matter why the model wrote the wrong thing, only that the wrong thing gets caught before being shown. This also directly fixes the confirmed `AnswerGate` blind spot from item 4 (global-blob matching), since a per-citation, per-file check inherently ties the quote to the specific file it's claimed to be from.

**For the "files are identical" fabrication, the same fix needs one addition to be complete**: that claim isn't a fabricated quote to verify against a single file — it's a false *comparative* claim (equivalence between two files) with no literal quoted string to check. A content-verification step scoped only to "does this quote appear in this cited file" would not, by itself, catch a false equivalence/no-difference claim. Closing that case too requires the verification step to also flag comparative claims ("identical," "same code," "no difference") between multiple cited files and check them against actual file equality (or at least a real diff), not just individual quote provenance.

**Recommendation for Pass 2 scope**: build the fix as two parts — (1) per-citation content verification (re-read cited file/line range, confirm quoted/paraphrased content is real) as the primary fix, directly closing the orchestrator case and the `AnswerGate` structural gap; (2) a narrower comparative-claim check (flag "identical"/"same"/"no difference" language spanning 2+ cited files, verify via real diff) to close the story-agent case specifically. Both are scoped, both are testable against these exact two reproduced-question-shapes before considering the fix complete.
