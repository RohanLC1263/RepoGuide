# RepoGuide Multi-Language Architecture

This document outlines how RepoGuide handles multi-language support across its pipeline, detailing the architecture, implementation specifics, and identifying gaps and hardcoded assumptions for future multi-language scaling.

## 1. Language Detection
**How it detects language:**
RepoGuide uses file extension string parsing to detect the programming language of a file.

**Where it happens:**
Language detection is centralized in `src/indexing/languageDetector.ts` through the `detectLanguage` and `getTreeSitterLanguage` functions. 

**Recognized languages:**
- TypeScript (`.ts`, `.tsx`)
- JavaScript (`.js`, `.jsx`)
- Python (`.py`)
- Java (`.java`, `.kt`)
- Go (`.go`)
- Rust (`.rs`)
- C++ (`.cpp`, `.c`, `.h`)
- Markdown (`.md`)

**Unrecognized extensions:**
When an extension is not recognized, `detectLanguage` returns `null`. Subsequent AST logic falls back to simple text-based processing (e.g., regex fallbacks or pure text chunking) or ignores the file entirely depending on the caller.

**Centralization:**
While the initial detection is centralized, the consumer mappings (such as what AST nodes represent a function) are scattered across `symbolExtractor.ts`, `astChunker.ts`, and `staticAnalyzer.ts`.

## 2. File Walking and Filtering
**File Inclusion Decision:**
The file walker logic lives in `src/indexing/fileWalker.ts`. A file is included if its extension matches a hardcoded `ALLOWED_EXTENSIONS` set.

**Filtering Rules:**
The walker filters out files using three merged lists:
1. `DEFAULT_IGNORES`: Hardcoded exclusions including `node_modules`, `dist`, `build`, `.git`, `.repoguide`, `target`, `logs`, `test_*`, `manual_*`, `*.min.js`, etc. (test and generated files are actively ignored).
2. `.gitignore`: Contents of the project's root ignore file.
3. User config: `repoguide.excludePatterns` fetched from VS Code workspace settings.

**File Budget:**
The file limit is enforced at the end of the `walkFiles` function in `src/indexing/fileWalker.ts`, and is now configurable (`repoguide.maxIndexedFiles`, default 2000, no longer a hardcoded constant). If the discovered file count exceeds the budget, files are scored (entry-point filename match, then most-recent mtime, then shallowest directory depth) and the top-scoring subset is kept; truncation is persisted and surfaced as a query-time evidence gap rather than only a `console.warn`.

## 3. Symbol Extraction
**Implementation & Parsers:**
Extraction happens in `src/indexing/symbolExtractor.ts`. It utilizes the `node-tree-sitter` parser. The currently available grammars defined in `package.json` are `tree-sitter-cpp`, `tree-sitter-go`, `tree-sitter-java`, `tree-sitter-python`, `tree-sitter-rust`, and `tree-sitter-typescript`.

**Node Mapping Strategy:**
A hardcoded dictionary `NODE_TYPES` maps AST node strings to RepoGuide kinds. For example, Rust uses `impl_item` and `trait_item` for classes, whereas Java uses `class_declaration`.

**Fallback logic:**
If the Tree-sitter parser fails or is unavailable:
- **TypeScript/JavaScript:** Falls back to regex via `extractTypeScriptSymbolsByRegex`.
- **Python:** Falls back to regex parsing `/^[ \t]*class\s+(\w+)/gm` and `/^[ \t]*(?:async\s+)?def\s+(\w+)/gm`.
- Other languages yield an empty symbol array.

## 4. Call Graph Construction
**V1 vs V2 Logic:**
- **V1 Builder (`callGraphV1Builder.ts`):** Relies heavily on language-agnostic but inaccurate regex scanning `/\b([A-Za-z_]\w*(?:\.[A-Za-z_]\w*)*)\s*\(/g`. It heavily assumes TS/JS and Python paradigms, trying to find `self`, `this`, and inferring class instances based on constructor types (`__init__`).
- **V2 Builder (`callGraphBuilderV2.ts` & `edgeResolver.ts`):** Uses the `FileStructure` payload generated by `staticAnalyzer.ts` (which natively traverses the AST). Edges are resolved dynamically based on actual function/method AST nodes rather than regex guesses.

**Hardcoded Assumptions & Value Flow Pass:**
- **`callGraphValueFlow.ts` was removed before this repo's tracked git history begins** (see `src/comprehension/comprehensionEngine.ts:24`'s `// removed CallGraphValueFlowPass` marker; the file survives only as a stale, gitignored `out/comprehension/callGraphValueFlow.js` build artifact, never rebuilt). Its JS/TS-biased array-literal regex scanning and its axios/yarn synthetic dynamic-dispatch edge injection (e.g. forcibly connecting `lib/defaults/index.js` to `xhr`, or hardcoding `getPluginConfiguration` edges for Yarn) do not run today. **This is a real, disclosed gap, not a hack to remove**: the current call-graph pipeline (`callGraphBuilderV2.ts`/`edgeResolver.ts`) has no dynamic-dispatch resolution at all for registry/factory-based indirection. A general fix exists as a reusable pattern (`src/indexing/semantic/providers/typescript/resolution/relationshipResolver.ts` resolves calls via the real TypeScript compiler API, `typeChecker.getResolvedSignature()`), but it feeds a different, separate pipeline (semantic/canonical facts) than the call-graph/`FlowExtractor` path this section describes, and `FlowExtractor`'s consumer (`FlowContextBuilder`) isn't currently constructed anywhere in `src/` either — porting real dynamic-dispatch resolution into the call-graph pipeline is a scoped feature, not a cleanup. See `docs/engineering-log/LANGUAGE_HACK_CLEANUP_REPORT.md` for the investigation that found this.
- `cleanTypeName` (in V1) hardcodes TS and Python type syntax: stripping `Optional[T]`, `Annotated[...]`, and `Promise<T>`.
- Python imports have special bespoke path-walking resolution logic to find `__init__.py` recursively (in `staticAnalyzer.ts`).

## 5. Chunking and Embedding
**Where chunking occurs:**
Chunking is orchestrated by `src/indexing/astChunker.ts`.

**Mechanism:**
It parses the AST and maps language-specific nodes (`RELEVANT_NODE_TYPES` like `method_definition`, `struct_specifier`) into discrete chunks. 
- Very large AST chunks are handed off to `splitLargeAstChunk`.
- If Tree-sitter fails, Python triggers a regex class/def fallback.

**Fallback Chunker:**
If no valid AST exists, it drops to `src/indexing/textChunker.ts`, which blindly slices text into 50-line overlapping windows (10-line overlaps).

## 6. Module Understanding
**Prompts:**
Module understanding logic lives in `src/comprehension/moduleUnderstandingBuilder.ts`. The prompt itself (lines ~190-227) is language agnostic, instructing the LLM to identify "classes, services, and core abstractions".

**Language Coupling:**
While the prompt is agnostic, the dependency boundaries it receives depend entirely on `staticAnalyzer.ts`. The import resolver hardcodes expectations for JavaScript (`index.ts`, `index.js`) and Python (`__init__.py`) to bridge files across module boundaries, affecting what the LLM believes is an "Export to other modules".

## 7. Query Pipeline Awareness
**Status:**
The query pipeline (`src/query/hybridRetrievalFusion.ts` and `src/prompts/chatPrompt.ts`) is completely decoupled from language-specific logic.

**Risks:**
Because the Chat Prompt builds its response purely on upstream metadata (`flowContext`, `taggedChunks`, `projectUnderstanding`), any language-specific extraction failures cascade blindly. If Go interfaces are poorly modeled in the Call Graph, the Query Pipeline will silently omit them from `flowContext` without realizing there is an architectural blindspot.
